# CAD Studio local automation queue protocol

## Purpose

The CAD Studio desktop client uses Tauri to persist jobs as local JSON files. A Python worker reads the queue and invokes local Codex. Normal desktop startup enables only the Codex handler; mock handlers require explicit development-test configuration.

## Queue directory

Rust uses `app.path().app_data_dir()/queue`. The current Tauri identifier remains:

```text
com.wzyn.cadstudio
```

Typical Windows location:

```text
%APPDATA%\com.wzyn.cadstudio\queue
```

The worker reads this directory by default. Override it for debugging:

```powershell
python -m apps.desktop.cad_workbench.queue_worker --queue-dir "<queue-directory>"
```

Desktop integration tests can set `CAD_STUDIO_QUEUE_DIR` before startup to override Tauri's queue directory. Normal execution without this variable uses the application-data directory.

Watch continuously:

```powershell
python -m apps.desktop.cad_workbench.queue_worker --watch --queue-dir "<queue-directory>"
```

Worker Control in the desktop queue panel starts and stops the application-managed Python worker. Browser preview mode does not start a worker.

## Job JSON

Each job has one file, named using its sanitized `id`:

```text
{id}.json
```

Example fields:

```json
{
  "schemaVersion": "1.0",
  "id": "job-1721900000000-a1b2c3",
  "runId": "run-1721900000000-a1b2c3",
  "kind": "create_shell",
  "title": "Create CAD task",
  "detail": "Create a part, assembly, enclosure, hole/slot, or basic-check task",
  "status": "queued",
  "progress": 0,
  "createdAt": "2026-07-25T12:00:00.000Z",
  "updatedAt": "2026-07-25T12:00:00.000Z",
  "requestedBy": "local-user",
  "createdByAppVersion": "0.1.0",
  "policy": {
    "sandbox": "workspace-write",
    "approval": "never",
    "requireSkillRead": true,
    "requireTests": true,
    "requireCommit": true,
    "requirePush": false,
    "requireReviewerPass": true
  },
  "capabilities": [],
  "projectPath": "D:/demo/demo_shell.step"
}
```

Machine-readable schema:

```text
apps/desktop/cad_workbench/schemas/automation_job.schema.json
```

Job kinds:

- `create_shell`: a legacy-compatible name for new CAD tasks, including parts, assemblies, enclosures, holes/slots, and basic checks.
- `import_model`: import a local CAD model and establish project context.
- `delivery_package`: generate STEP, STL, PDF, DWG, or other deliverables.
- `codex_task`: a noninteractive Codex execution task generated from graphical configuration.

Codex Bridge extension fields:

```json
{
  "executor": "codex",
  "objective": "Select the CAD task type, manufacturing process, material, and delivery formats from the user's requirements",
  "target": "AI automatic selection",
  "expectedOutput": "AI automatic output selection",
  "strictRules": ["Choose an engineering solution for unspecified fields", "Holes and slots must be actual geometry cuts", "Review CAD drawings against common GB/T mechanical drawing conventions"],
  "prompt": "You are Codex. Execute the task generated by CAD Studio...",
  "cwd": "C:/path/to/solidworks-automation-skill",
  "skillPath": "C:/path/to/solidworks-automation-skill/SKILL.md",
  "uiConfig": {
    "selection": {
      "mode": "auto_best",
      "autoTarget": true,
      "autoOutput": true,
      "autoProcess": true,
      "autoMaterial": true,
      "instruction": "Choose an engineering solution for unspecified fields and explain the reasons."
    }
  }
}
```

Automatic-selection semantics:

- When the user has not specified task type, process, material, output formats, or dimensional details, the UI writes `selection.mode = "auto_best"`.
- Codex selects an approach based on the engineering objective, input files, manufacturing process, cost, strength, machinability, and delivery requirements.
- The final result must explain the selection and residual risks.
- A template or option explicitly selected by the user takes precedence for that field.

State transitions:

```text
queued -> running -> passed | review_required | failed | cancelled
queued -> running -> failed
queued -> cancelled
queued -> approval_required -> queued | cancelled
review_required -> passed | failed
```

Conventions:

- The UI creates jobs through a create-only interface. Cancellation, pre-execution approval, and post-execution manual review use dedicated commands; generic saves must not overwrite job state.
- The worker processes only `status == "queued"` jobs.
- `passed`, `failed`, and `cancelled` are terminal states. `review_required` requires explicit user approval or rejection of the review.
- The worker writes `workerLog`, `lastMessage`, `result`, or `error` for direct frontend display.
- Successful jobs receive `artifactLedgerPath` and `artifacts` for existence, size, and hash display.
- Successful jobs receive `reviewGatePath` and `reviewGate` for artifact review status.
- A Reviewer Gate `warning` produces `review_required` and must not be shown as complete. Only a gate `pass` produces `passed`.
- Real CAD handlers must check file existence before writing `passed`. Placeholders, AI JSON receipts, and old files must not be labeled as manufacturing deliverables.
- `save_queue_job` accepts only new, nonexistent jobs in `queued` state and rejects overwriting existing jobs.

Manual approval requires a specific explanation and completion of the current job's review checklist. Approval records `reviewedBy`, `reviewedAt`, and `reviewDecision = "approved"`; it stores manual checks, warnings, and a path/size/SHA-256 artifact snapshot in `reviewGate.manualReview` and audit event `review.manual_approved`. Rejection requires an issue description and records `reviewDecision = "rejected"`, an explicit error, and `review.manual_rejected`.

## Policy Gate

Policy Gate is enforced at the worker/control-plane layer; frontend messaging alone is insufficient. Before execution, Codex jobs are checked against policy and capability declarations. A risky job receives:

```json
{
  "status": "approval_required",
  "approvalReasons": ["This task requests Git push and requires manual approval."],
  "lastMessage": "Manual approval required: ..."
}
```

Manual approval is currently required when:

- `policy.approval == "manual-required"`.
- `policy.requirePush == true` or `uiConfig.gates.commitAndPush == true`.
- `policy.sandbox == "danger-full-access"`.
- `capabilities` contains `git_push`, `full_access`, `cad_macro`, `external_network`, `cross_workspace`, or `delete_files`.

Desktop approval writes:

```json
{
  "approvedAt": "unix:1784970000",
  "approvedBy": "local-user",
  "approvedPolicyReasons": ["This task requests Git push and requires manual approval."],
  "status": "queued"
}
```

The worker recalculates the current approval reasons and requires an exact match with `approvedPolicyReasons`. Adding full access, CAD macros, or another risky capability after approval invalidates approval and returns the job to `approval_required`. This is not a complete tamper-resistance solution; HMAC signatures and immutable audit records are planned for the Artifact Ledger.

## Reliable queue state machine

The queue still uses local JSON files, with these minimum reliability semantics:

- Before claiming a job, open `{job}.json.lock` and acquire an exclusive OS lock using `msvcrt.locking` on Windows or `fcntl.flock` on Unix, preventing duplicate claims by multiple workers.
- After claiming, write `runnerId`, `workerPid`, `attempt`, `heartbeatAt`, and `leaseUntil`.
- During execution, refresh `heartbeatAt` and `leaseUntil` periodically so long jobs are not incorrectly treated as stale.
- Release the OS lock when execution ends. Keep the `.lock` file for diagnostics. The OS also releases the lock on an abnormal process exit.
- A UI cancellation (`status: "cancelled"` or `cancelRequested: true`) causes the worker to terminate its managed Codex child process.
- On startup or polling, restore `running` jobs with expired `leaseUntil` to `queued`.
- On explicit worker stop, Alt+F4, system shutdown, or native exit, terminate the worker process tree, then immediately requeue unfinished `running` jobs belonging to that `workerPid`. Jobs already requesting cancellation remain `cancelled`.
- Move corrupt JSON to `queue/quarantine` and create a matching `.error.txt` without interrupting the watch loop.
- Write per-job events to `queue/events/{job_id}.jsonl`.
- Write managed child-process stdout/stderr to `queue/logs/{job_id}.stdout.log` and `queue/logs/{job_id}.stderr.log`.
- Write successful-job ledgers to `queue/ledgers/{job_id}.ledger.json`.
- Write successful-job Reviewer Gate reports to `queue/reviews/{job_id}.review.json`.
- Write health heartbeats to `queue/worker_health.json`.

These are worker-managed fields: the UI may display them but must not modify them manually.

## Worker Health

After each queue scan, the worker writes:

```text
queue/worker_health.json
```

Fields include:

- `status`: `healthy`, `attention`, `warning`, or `error`.
- `heartbeatAt`: time of the latest heartbeat.
- `processedCount`: jobs processed in this scan.
- `recoveredCount`: stale running jobs recovered in this scan.
- `queue`: counts by job state.

The desktop `worker_status` command returns the managed PID and latest health heartbeat. Browser preview does not start a worker.

## Artifact Ledger

Artifact Ledger turns Agent delivery results into auditable machine records. After success, the worker collects `result.outputPath`, `result.outputs`, `result.artifacts`, and the job's own `artifacts` fields:

```json
{
  "schemaVersion": "1.0",
  "jobId": "job-1721900000000-a1b2c3",
  "runId": "run-1721900000000-a1b2c3",
  "status": "passed",
  "artifacts": [
    {
      "kind": "step",
      "path": "D:/demo/outputs/model/demo.step",
      "exists": true,
      "isDirectory": false,
      "sizeBytes": 12345,
      "sha256": "..."
    }
  ],
  "verification": [],
  "resultMessage": "Task completed"
}
```

Destination:

```text
queue/ledgers/{job_id}.ledger.json
```

Resolve relative outputs first against the job's `cwd`; without `cwd`, resolve against the parent of `projectPath` or the project directory. Summarize the same information into the job's `artifactLedgerPath` and `artifacts` and append `artifact.ledger_written`. Real CAD handlers remain responsible for determining whether all P0 deliverables are present. The ledger records facts and does not replace manufacturing acceptance.

## Reviewer Gate

Reviewer Gate builds a minimum artifact review report from Artifact Ledger:

```text
queue/reviews/{job_id}.review.json
```

Current rules:

- No declared artifacts: `warning`; workflow completion alone cannot establish manufacturing-file completeness.
- Declared artifact missing: `fail`.
- Empty artifact: `fail`.
- Directory artifact: `warning`; directory contents are not currently checked recursively.
- Existing ordinary file with SHA-256: `pass`.
- Codex verification `failed`: gate must `fail`. Missing verification or residual risks require at least `warning`.
- Explicit format lists such as `SLDPRT / STEP / STL` or `DWG / DXF / PDF` are checked item by item; one file cannot stand in for the full delivery package.
- Codex artifacts must be inside the task workspace, user output directory, or input-file directory. Before execution, record CAD file sizes, nanosecond modification times, and SHA-256. After execution, only new files or changed content hashes receive `producedThisRun = true`; timestamp-only changes do not qualify. AI receipts and unchanged old files are not CAD outputs of the current run.
- STEP/STP must contain `ISO-10303-21` and `END-ISO-10303-21` markers.
- STL must have recognizable ASCII `solid/endsolid` or basic binary STL structure.
- DXF must contain `SECTION` and end with `EOF`.
- PDF must have a `%PDF-` header.
- DWG must have an AutoCAD `AC10` version header.
- Proprietary SLDPRT and SLDASM currently receive only `warning`; opening and reviewing them in SolidWorks is future work.

The report summary is written to `reviewGate` and `reviewGatePath`, and `review.gate_completed` is appended. This is a foundation for manufacturing-grade review. Real CAD work still requires checking that STEP/STL/DWG/PDF files open, dimension chains are complete, and 3D-printed openings are actual geometry cuts.

## Codex Bridge

The application is an AI-assisted CAD automation console:

```text
Graphical configuration -> Structured job JSON -> Python worker -> codex exec -> Queue result update
```

Before compiling a prompt, the worker performs local-first RAG over the main Skill, `references/`, and subskill knowledge files, injecting sources, SHA-256, and excerpts. When `uiConfig.knowledgeBase.cloudEnabled=true`, Tauri derives `external_network` capability on the backend. HTTPS cloud retrieval is permitted only after manual approval.

Enable Codex execution:

```powershell
python -m apps.desktop.cad_workbench.queue_worker --watch --enable-codex --queue-dir "<queue-directory>"
```

Starting from the application runs the equivalent command with the Tauri queue directory. It does not add `--codex-full-access`; full access still requires approval and the explicit switch.

The worker invokes:

```powershell
node.exe "<npm>/node_modules/@openai/codex/bin/codex.js" exec -C "<cwd>" -s workspace-write -c "approval_policy=\"never\"" -o "<output-file>" --output-schema "<schema>" "<prompt>"
```

Notes:

- Explicit `--enable-codex` avoids triggering real Codex runs during ordinary mock debugging.
- Only `workspace-write` is allowed by default. Full access requires Policy Gate approval and `--codex-full-access` at worker startup.
- Windows npm installations prefer `node.exe + codex.js` and do not pass user prompts through `cmd.exe` parsing.
- Codex version, login, and SolidWorks preflight health checks have 5–10 second timeouts. A timeout terminates the process tree and returns a clear error without blocking the desktop interface.
- The worker checks that `cwd` lies within the repository allowlist and forces output to `<cwd>/ai_team/{job_id}_codex_result.json`. It deletes an old same-named receipt before execution; missing or invalid JSON fails the job.
- The UI generates prompts and constraints; Codex reads/writes files, invokes skills, validates, and performs authorized commit/push actions.
- Before execution, local mechanical-knowledge retrieval injects source paths, SHA-256, scores, and excerpts into the enterprise prompt.
- Settings accept local standards-library directories. Cloud RAG is off by default; enabling it causes backend derivation of `external_network` and requires approval.
- The result is saved to `ai_team/{job_id}_codex_result.json`, with its path written to `result.outputPath`.

### CAD application routing

The UI writes the target application to `targetSoftware` and `uiConfig.cadRuntime`:

```json
{
  "targetSoftware": "AI automatic application selection",
  "capabilities": ["cad_macro"],
  "policy": {
    "sandbox": "danger-full-access",
    "approval": "never"
  },
  "uiConfig": {
    "cadRuntime": {
      "application": "auto",
      "applicationLabel": "AI automatic application selection",
      "localCadAutomation": true,
      "solidworksSkillPath": "C:/path/to/solidworks-automation-skill/SKILL.md",
      "autocadSkillPath": "C:/path/to/solidworks-automation-skill/subskills/autocad-automation/SKILL.md"
    }
  }
}
```

Routing rules:

- Prefer SolidWorks for 3D solids, assemblies, actual geometry cuts, sheet metal, and STEP/STL/SLDPRT export.
- Prefer AutoCAD for DWG/DXF/PDF, GB/T drawings, layers, dimension chains, hole tables, title blocks, and native AutoCAD previews.
- Delivery packages, assembly drawings, and manufacturing review may use SolidWorks for 3D and intermediate files, followed by AutoCAD for 2D drawings and exports.
- With `application == "auto"`, Codex must choose SolidWorks, AutoCAD, or both from the objective and explain its reasons in the result.
- With `localCadAutomation == true`, the job declares `cad_macro` and `danger-full-access`, requiring Policy Gate approval. The worker must also be started with `--codex-full-access` before an approved job can invoke desktop software.

## Connecting real executors

Python worker extension point:

```text
apps/desktop/cad_workbench/queue_worker.py
```

Replace or inject handlers:

- `create_shell`: SolidWorks modeling, actual solid cuts, and STL/STEP export.
- `import_model`: file parsing, thumbnails, and project-directory initialization.
- `delivery_package`: AutoCAD drawing export, PDF/DWG/DXF, delivery lists, and standards review.

Executors must obey P0 gates:

- 3D-print openings must be actual geometry cuts, not lines or annotations alone.
- Drawings must retain complete dimension chains, hole tables, technical requirements, drawing frames/title blocks, and GB/T-style annotations.
- On failure, write `failed` and a clear `error`; do not silently skip the step.
